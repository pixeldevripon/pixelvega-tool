# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

NestJS · Prisma 7 (driver adapters, `@prisma/adapter-pg`) · PostgreSQL (Neon) · better-auth via `@thallesp/nestjs-better-auth` · Cloudinary (image storage) · pnpm.

## Commands

```bash
pnpm install                 # install deps
pnpm start:dev                # dev server, watch mode (port from .env PORT, default 3000) — runs `prisma migrate deploy` first (prestart:dev)
pnpm build                    # nest build
pnpm start:prod                # node dist/main — runs `prisma migrate deploy` first (prestart:prod)

pnpm lint                     # eslint --fix over src,apps,libs,test
pnpm format                   # prettier --write over src/test

pnpm test                     # jest unit tests (rootDir: src, pattern *.spec.ts)
pnpm test -- path/to/file.spec.ts   # run a single unit test file
pnpm test:watch
pnpm test:cov
pnpm test:e2e                 # jest -c test/jest-e2e.json (currently stale — see Testing note below)

npx tsc --noEmit               # typecheck only, no build output
```

Seeding:

```bash
pnpm seed                     # wipe every seeded table, then insert the full test dataset
pnpm seed:reset               # prisma migrate reset --force (drops schema, reapplies migrations, then runs the seed)
npx prisma db seed            # same seed, driven by prisma.config.ts migrations.seed
```

`pnpm seed` **deletes every row in every application table** (one `TRUNCATE ... CASCADE`, table list hand written in `prisma/seed/reset.ts`, `_prisma_migrations` deliberately excluded) and rebuilds a full dataset: at least 100 rows in all 30 tables. It refuses to run when `NODE_ENV=production` unless `--force` is passed.

- `prisma/seed.ts` is the entry point and orchestrates the run; `prisma/seed/*.ts` holds one module per concern (`config.ts` for volumes, `random.ts` for the seeded generator, `pools.ts` for text data, then `users`/`reference`/`leave`/`projects`/`documents`/`time-tracking`/`workflow`/`work-reports`/`ai`/`logs`).
- `config.ts` is the only file to edit for data volume, the shared password, or the fixed date the history is built backwards from. Everything is generated from `RANDOM_SEED` via a mulberry32 generator, so the same seed always produces the same rows and the same ids, which is what lets a Postman collection keep real ids as default variable values.
- Passwords are real: one `hashPassword()` from `better-auth/crypto` is written to every `Account` row (`providerId: 'credential'`), so every seeded account can actually sign in. `TEST_ACCOUNTS` in `config.ts` defines one always ACTIVE, always verified login per role (`admin@`/`pm@`/`developer@`/`designer@`/`client@pixelvega.com`, plus the `SEED_ADMIN_EMAIL` system admin), and `GUARANTEED_TEST_PROJECTS` wires the first 14 projects to them so each of those logins has projects, hours, work reports, blockers, and feedback rather than depending on the random draw.
- The seed reproduces the service layer's own invariants rather than just filling columns: `Project.actualHours` is recomputed as `sum(durationMinutes where endedAt is not null)/60`; approved additional requirements and resolved blockers are added onto `estimatedHours`/`deadline` the additive way the app does it; a `RUNNING` time entry has null `endedAt`/`durationMinutes`, is dated on the real current UTC day, and never coexists with another running timer for the same person across `TimeEntry` and `MeetingTimeEntry`; `LeaveBalance.usedDays` equals the summed days of that user's APPROVED requests for the year; review and feedback rounds start at 1 and never skip; a `WAITING_FOR_FEEDBACK` project has no `ClientFeedback` yet, because the first round is what would move it. Keep these in step when a new feature lands, otherwise seeded rows start contradicting what the read endpoints assume.

Prisma:

```bash
npx prisma migrate dev --name <name>   # create + apply a migration against Neon (interactive — needs a TTY)
npx prisma migrate deploy               # apply pending migrations non-interactively (CI, scripts, this session)
npx prisma generate                     # regenerate the client (needed after any schema.prisma edit)
npx prisma studio                       # inspect data
npx prisma validate                     # schema-only validation
```

`migrate dev` refuses to run in a non-interactive shell whenever it needs to ask a yes/no confirmation (e.g. a "this might cause data loss" prompt) — it errors with "Prisma Migrate has detected that the environment is non-interactive." When that happens (as it will for any agent/script driving this repo), hand-write the migration folder/`migration.sql` yourself under `prisma/migrations/<timestamp>_<name>/` and apply it with `migrate deploy`, which never prompts.

`prisma migrate deploy` also runs automatically before `start`/`start:dev`/`start:debug`/`start:prod` via `pre*` npm-lifecycle scripts in `package.json` (pnpm runs `pre<script>` before `<script>` for any script name, not just the handful npm reserves this for) — so pointing `DATABASE_URL` at a brand-new, empty Neon database and running `pnpm start:dev` is enough on its own: migrations create every table first, then the app boots. No separate manual `migrate deploy` step needed for local/dev use. This does mean a bad migration applies automatically on `start:prod` too, with no manual gate — acceptable for this project's current single-developer workflow, but worth revisiting if a review step before production migrations ever becomes necessary.

The first user (a `SYSTEM_ADMIN`, needed before anyone can hit `POST /users/invite`) is bootstrapped automatically on that same startup — no manual command. See "Roles & authorization" below.

`.env.example` (repo root, git-tracked — unlike `.env`/`CLAUDE.md`) is the source of truth for every env var this app reads; its own header comment says to keep it in sync whenever a new one is introduced. Keep that habit going forward rather than letting env vars go undocumented there.

## Architecture

### Global request pipeline (`main.ts` / `app.module.ts`)

- Global prefix is `api` and `ValidationPipe({ whitelist: true, transform: true })` is applied globally — new DTOs don't need per-route pipes, but any field not declared on the DTO is silently stripped rather than erroring.
- `NestFactory.create` passes `bodyParser: false` because better-auth parses the body itself; don't re-enable it or better-auth's routes break.
- `ThrottlerGuard` is registered as the global `APP_GUARD` at 20 requests/60s — this applies to **every** route by default, not just auth. `src/modules/auth/auth.controller.ts` overrides it tighter per-route with `@Throttle(...)` (3/60s on forgot-password, 5/60s on verify/reset) since those are more sensitive than the global default.
- CORS origin comes from `CORS_ORIGIN` env (falls back to `*`) with `credentials: true` — required for the `better-auth.session_token` cookie to be sent cross-origin.

### Prisma 7 + better-auth: non-obvious wiring

This project hit several Prisma-7 / better-auth integration issues that aren't documented anywhere obvious — know these before touching `src/auth/auth.instance.ts` or `prisma/schema.prisma`:

- **No `url` in `schema.prisma`'s `datasource` block.** Prisma 7 removed it; the connection string lives only in `prisma.config.ts` (`datasource.url`). Every `PrismaClient` construction in the app must instead pass an explicit driver adapter: `new PrismaClient({ adapter: new PrismaPg(new Pool({ connectionString: process.env.DATABASE_URL })) })`. See `src/prisma/prisma.service.ts` for the canonical pattern — reuse it anywhere else a `PrismaClient` is constructed outside Nest's DI (e.g. `auth.instance.ts`).
- **`auth.instance.ts` loads before `ConfigModule` populates `process.env`.** It's a plain module imported at the top of `app.module.ts`, so its top-level code (building the `pg.Pool`, reading `BETTER_AUTH_SECRET`) runs before Nest ever instantiates `ConfigModule.forRoot()`. It must `import 'dotenv/config'` itself at the top — don't remove that import.
- **better-auth's `basePath` must be the literal final path** (`/api/auth`), not just `/auth` "combined with the global prefix." `@thallesp/nestjs-better-auth`'s `AuthModule` mounts its middleware inside `onModuleInit()`, which runs during `NestFactory.create()` — before `main.ts` ever calls `app.setGlobalPrefix('api')`. Relying on prefix composition silently mounts routes at the wrong path with no error.
- **`@Hook()` / `@AfterHook()` providers require `hooks: {}` in the `betterAuth(...)` config**, or the library throws `Detected @Hook providers but Better Auth 'hooks' are not configured` at startup. See `src/auth/login-status.hook.ts`.
- **Password hashing / signed tokens reuse better-auth's own crypto, not a new dependency.** `better-auth/crypto` exports `hashPassword`, `verifyPassword`, `signJWT`, `verifyJWT` — used in `src/modules/auth/auth.service.ts` for the custom reset-password flow (not better-auth's own built-in reset-password, which uses email links rather than 6-digit codes). Credential account passwords live in `Account.password` (`providerId: 'credential'`), never in `User.password` (that column is unused by better-auth, kept only for schema completeness).
- **The `dotenv/config` load-order trap isn't unique to `auth.instance.ts`.** Any file with module-load-time code that reads `process.env` (i.e. runs at import time, not inside a function/constructor) hits the same issue, because such files get `require`d while building the module graph — before `main.ts`'s `bootstrap()` ever runs, let alone `ConfigModule.forRoot()`. `src/modules/uploads/cloudinary.service.ts` is a second example: `cloudinary.config()` runs at the top of the file, so it needs its own `import 'dotenv/config'` too.
- `NODE_ENV` gates `auth.instance.ts`'s `disableOriginCheck` (`true` unless `NODE_ENV === 'production'`) — relevant if login/session requests ever start getting rejected in a deployed environment where `NODE_ENV` isn't actually set to `production`.

### Roles & authorization model

- Global `AuthGuard` (from `@thallesp/nestjs-better-auth`) protects every route by default — session cookie is `better-auth.session_token`. Use `@AllowAnonymous()` to opt a route out (see `modules/auth/auth.controller.ts`).
- No better-auth `admin` plugin, no `ac`/roles config. Authorization is entirely the `role` column on `User`, a real Prisma `enum Role { SYSTEM_ADMIN ADMIN PROJECT_MANAGER DEVELOPER DESIGNER CLIENT }` (DB-enforced, and `Role` is importable from `@prisma/client` — use its members, not string literals, everywhere a role is compared or listed), gated per-route via `@Roles([...])`.
- **Always import `Roles` from `src/common/decorators/roles.decorator.ts`, never directly from `@thallesp/nestjs-better-auth`.** It wraps the library's decorator and unconditionally unions in `SYSTEM_ADMIN`/`ADMIN`, so every role-gated route is reachable by both without listing them — a new ADMIN-only (or any-role-only) endpoint just lists the roles that aren't already ADMIN/SYSTEM_ADMIN. This is a route-level bypass only: it can't express target-specific rules (see below), which live in the service layer instead.
- `SYSTEM_ADMIN` is a single, fixed root account: bootstrapped automatically by `SystemAdminBootstrapService` (`src/modules/users/system-admin-bootstrap.service.ts`, an `OnApplicationBootstrap` hook) the moment the `User` table is completely empty, using `SEED_ADMIN_EMAIL`/`SEED_ADMIN_NAME` from `.env` — same temp-password/invite-email flow as `UsersService.invite()`. Runs on every boot; it's a no-op once any user exists, and just logs a warning (doesn't crash startup) if the env vars aren't set. There's no API path to create a second `SYSTEM_ADMIN` — `InviteUserDto`/`UpdateUserDto` both exclude it from their allowed `role` values.
- `UsersService` (`invite`/`update`/`remove`) enforces the fine-grained protections that `@Roles([...])` can't express, keyed off the _target_ user's current role and passed-in `actorRole`:
  - Nobody can invite a new `ADMIN` unless the actor is `SYSTEM_ADMIN` (so a plain ADMIN can only invite PROJECT_MANAGER/DEVELOPER/DESIGNER/CLIENT).
  - An `ADMIN` cannot edit, delete, or change the role of another `ADMIN` or of the `SYSTEM_ADMIN` at all — only `SYSTEM_ADMIN` can. The `SYSTEM_ADMIN` account itself can never be deleted, by anyone.
  - Nobody (including `SYSTEM_ADMIN`) can change their own `role` via `PATCH /users/:id`.
  - Read routes (`GET /users`, `GET /users/:id`) aren't restricted this way — only the mutating ones.
- `User.status` (`INVITED | ACTIVE | SUSPENDED`) flips `INVITED → ACTIVE` automatically on first successful login via the `@AfterHook('/sign-in/email')` provider in `src/auth/login-status.hook.ts`.
- Soft delete: `User.deletedAt`. `UsersService.findAll/findOne` filter it out; `DELETE /users/:id` sets it rather than removing the row.
- `docs/ROLES_AND_PERMISSIONS.md` (gitignored, like the other `docs/features/*` design docs referenced elsewhere in this file) has the fuller spec-level writeup of this role/permission model — check it for intent behind a rule if this section doesn't cover the specific case.

### User profiles

- Two 1:1 extension tables off `User`: `EmployeeProfile` (ADMIN/PROJECT_MANAGER/DEVELOPER/DESIGNER) and `ClientProfile` (CLIENT) — see `prisma/schema.prisma`. Which one applies is derived live from `User.role` via `isClientRole()` in `src/modules/profiles/profiles.service.ts`; there's no separate stored flag.
- Profile rows are created automatically by `UsersService.invite()` calling `ProfilesService.createForRole()` right after the `User` row exists — `SystemAdminBootstrapService` does the same for the bootstrap `SYSTEM_ADMIN`. Any `User` created outside those paths (e.g. a direct `auth.api.signUpEmail` call) has no profile row until one is created by hand.
- `User.avatarUrl` / `avatarPublicId` live on `User` itself (shared across both profile types), not duplicated per-profile table.
- `EmployeeProfile` has two independent status fields, easy to conflate: `availabilityStatus` (informational-only staffing signal — see "Project management" below) and `currentStatus` (`EmployeeWorkStatus`: `WORKING`/`ON_LEAVE`, set via `PATCH /profiles/me` in `profiles.service.ts`).
- Changing a user's `role` across the CLIENT ↔ staff boundary via `PATCH /users/:id` does **not** migrate or create the matching profile row — a subsequent `PATCH /profiles/me` would then fail looking up the now-wrong table. Not currently guarded against; flag it if that role transition becomes a real workflow.

### Audit logging

- `AuditLogModule` (`src/modules/audit-log/`) is `@Global()`, like `PrismaModule` — inject `AuditLogService` anywhere without importing the module.
- `AuditLogService.log({ userId, action, targetType, targetId, metadata })` is called explicitly at meaningful points, not via a generic request interceptor — action names are dot-namespaced strings (`user.invited`, `user.updated`, `user.deleted`, `user.password_changed`, `user.password_reset`, `profile.updated`, `profile.avatar_updated`). `userId` is the **actor** performing the action, not necessarily the target (e.g. an ADMIN editing another user's role).
- `UsersService.update()` diffs `name`/`role`/`status` against the pre-update row and only logs `user.updated` (with `{ changes: { field: { from, to } } }` in `metadata`) when something actually changed — a no-op PATCH produces no audit row.
- `GET /audit-logs` (`@Roles(['ADMIN'])`, which — per "Roles & authorization" above — also admits `SYSTEM_ADMIN`; `src/modules/audit-log/audit-log.controller.ts`) is paginated and filterable by `targetType`/`targetId`/`userId`, newest first.
- Not yet instrumented: nothing in `auth.controller.ts`'s login/logout flow or `login-status.hook.ts` writes audit rows (e.g. suspended-login-blocked, first-login activation) — only the explicit service-level actions above do.

### File uploads

- `src/modules/uploads/` is generic image-storage infra (Cloudinary), not tied to profiles — `CloudinaryService.upload(buffer, folder, resourceType)` / `delete(publicId, resourceType)` can back any feature's file needs by importing `UploadsModule`, no profile-specific coupling. `resourceType` is Cloudinary's own distinction: `'image'` (default) unlocks image transforms, `'raw'` is required for anything else (pdf, docx, zip, ...) — project documents pick one or the other per-file based on `file.mimetype.startsWith('image/')`.
- `POST /profiles/me/avatar` is intentionally `POST`, not `PATCH`: each upload creates a brand-new Cloudinary asset (new `publicId`/URL every call — not idempotent) and deletes the previous one afterward. Plain field edits stay on `PATCH /profiles/me`, whose `UpdateProfileDto` deliberately excludes `avatarUrl`.
- Two separate multer configs, both in `src/modules/uploads/`: `imageUploadOptions` (avatars — images only, smaller size cap) and `documentUploadOptions` (project documents — images plus a wider office/archive-format allowlist: PDF, Word, Excel, PowerPoint, zip, plain text/CSV; 25MB cap). Adding a new allowed document MIME type means editing `ALLOWED_DOCUMENT_MIME_TYPES` in `document-upload.options.ts` (e.g. the PowerPoint types were added there after upload failures on real `.ppt`/`.pptx` files).
- Multer's `FileInterceptor`/`FilesInterceptor` (`@nestjs/platform-express`) parses multipart bodies itself and works independently of `main.ts`'s `bodyParser: false` (which is only there for better-auth) — no extra wiring needed for new upload routes.
- Env vars: `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET`.

### Leave management

- `src/modules/leave/` covers four models in one module: `LeaveType` and `Holiday` are ADMIN-managed reference data (everyone can read, only ADMIN writes); `LeaveRequest` and `LeaveBalance` are the actual workflow.
- Creating a leave request (`POST /leave-requests`, any of ADMIN/PROJECT_MANAGER/DEVELOPER/DESIGNER) never checks balance — it's always created `PENDING` even if it exceeds what's left. Balance is only touched at approval time: `LeaveRequestsService.approve()` increments `LeaveBalance.usedDays`; `reject()` leaves it untouched.
- `LeaveBalance` rows are lazy get-or-create, keyed on `(userId, leaveTypeId, year)` — see `LeaveBalancesService.getOrCreate()`. There's no cron job and no year-end carry-forward; the row is created the first time it's read or incremented, seeded from `LeaveType.defaultDaysPerYear`.
- `GET /leave-requests` scope differs by role: ADMIN sees every request regardless of status; PROJECT_MANAGER is filtered server-side to `PENDING`/`APPROVED` only via a `where: { status: { in: [...] } }` allowlist in `LeaveRequestsService.findAll()` — REJECTED (and CANCELLED) must never reach a PROJECT_MANAGER, and using an allowlist rather than a denylist means any future status added to the enum is excluded by default rather than accidentally leaking through.
- There's still no per-PM/per-developer assignment scoping in leave visibility (e.g. "only the developers I manage") — even though `ProjectMember` now exists (see "Project management" below), `LeaveRequestsService.findAll()` doesn't cross-reference it; a PROJECT_MANAGER sees every PENDING/APPROVED request company-wide, not just their own project's staff. Flag this if project-based leave scoping becomes a real requirement.
- A requester can cancel their own request via `PATCH /leave-requests/:id/cancel`, but only while it's still `PENDING` — ownership and status are both checked in the service, not just the route guard.
- `Holiday.startDate`/`endDate` model a range (equal for a single day) rather than one row per day. `days` on both `Holiday` and `LeaveRequest` API responses is computed on the way out via `daysBetweenInclusive()` (`src/common/utils/date.util.ts`), not stored — avoids a derived column drifting out of sync with the dates. `POST /holidays` only requires `startDate`; omitted `endDate` defaults to `startDate`.
- `Holiday` has `@@unique([name, startDate])` specifically so a reseed script can `upsert` instead of needing a fragile existence check.

### Project management

- `src/modules/projects/` covers `Project`, `ProjectMember` (staffing), `ProjectTypeTag`, `ProjectActivity`, `ProjectDocument`, `TimeEntry`, `MeetingTimeEntry`, `AdditionalRequirement`, `DailyWorkReport`/`DailyProjectEntry`, `Blocker`, `BlockerReason`, `ProjectInternalReview`, and `ClientFeedback` across thirteen controllers in one module: `ProjectsController` (project CRUD/status/priority/types/archive/estimated-hours), `ProjectMembersController` (staffing, nested under `projects/:projectId/members`), `ProjectDocumentsController` (documents, nested under `projects/:projectId/documents`), `ProjectTimeEntriesController` (time tracking, nested under `projects/:projectId/time-entries`), `TimeEntriesController` (the one exception to project-nesting for time tracking — `GET /time-entries/active`, since the one-active-timer rule is global), `AdditionalRequirementsController` (nested under `projects/:projectId/additional-requirements`), `DailyWorkReportController` (self-scoped, top-level `daily-work-reports/*` — a report spans multiple projects at once, so it can't be project-nested), `ProjectDailyWorkReportsController` (the project-nested counterpart, `projects/:projectId/daily-work-reports`, mirroring the `TimeEntriesController`/`ProjectTimeEntriesController` split), `BlockersController` (top-level `blockers/*` — report/update a blocker without needing a project-scoped route), `ProjectBlockersController` (the project-nested PM dashboard, `projects/:projectId/blockers`), `BlockerReasonsController` (global reference data, top level `blocker-reasons/*`), `InternalReviewsController` (nested under `projects/:projectId/internal-reviews`), and `ClientFeedbackController` (nested under `projects/:projectId/client-feedback`).
- **Status** is a fixed state machine — `ALLOWED_STATUS_TRANSITIONS` in `projects.service.ts` is the only source of truth for which `ProjectStatus` moves are legal (`PATCH /projects/:id/status`). Moving to `ON_HOLD` or `CANCELLED` requires a `reason`; only `ADMIN`/`SYSTEM_ADMIN` can move a project to `CANCELLED`, and only `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` can move a project to `ON_HOLD` (`DEVELOPER`/`DESIGNER` are blocked from this one specific transition even though they can otherwise change status through this same endpoint). `COMPLETED` sets `completedAt`. `COMPLETED` and `CANCELLED` are not fully terminal: each has exactly one outgoing transition, back to `READY_FOR_WORK` (`updateStatus()`'s `isReopening` branch), restricted to `ADMIN`/`SYSTEM_ADMIN`, rejected with a 409 if the project has already been archived (use restore instead, see below), and clearing `completedAt`/`cancellationReason` on the way. There is no time limit on this. Every other status truly has no outgoing transitions once reached.
- **Archive/restore is a separate flag layered on top of status, not part of the state machine above.** `PATCH /projects/:id/archive` (`ProjectsService.archive()`, ADMIN/SYSTEM_ADMIN only) sets `archivedAt`, only when the project's current status is `COMPLETED` or `CANCELLED` (409 otherwise, and 409 if already archived); it does not touch `status` itself. `PATCH /projects/:id/restore` (`ProjectsService.restore()`, same role gate, 409 if not archived) is the only way back from an archived project: it clears `archivedAt`/`completedAt`/`cancellationReason` and unconditionally sets `status: READY_FOR_WORK`, regardless of whether the project was `COMPLETED` or `CANCELLED`, and with no time limit. Both log their own `ProjectActivityType` (`PROJECT_ARCHIVED`/`PROJECT_RESTORED`). `QueryMyProjectsDto`'s `archived` query param is a read-side filter on `archivedAt` only, unrelated to either of these writes.
- **Priority** (`PATCH /projects/:id/priority`) requires `rushReason` when set to `URGENT`/`CRITICAL`; the field is cleared back to `null` if priority moves off those two values.
- **Project types are a join table (`ProjectTypeTag`), not an array column or single enum field** on `Project` — because a project needs _one or more_ `ProjectType`s at once (e.g. WordPress + SEO), not just one; `@@unique([projectId, type])` prevents double-tagging the same type. `PATCH /projects/:id/types` is **replace-all, not a delta** — the caller sends the full desired set and `ProjectsService.updateTypes()` diffs it against what's currently tagged, only writing/logging an activity when something actually changed.
- **Staffing (`ProjectMember`) is append-only history**, the same pattern as `ProjectActivity`: adding a member always inserts a new row; removing sets `leftAt` rather than deleting, so a user who rejoins later gets a brand-new row and past rows are untouched. Only `leftAt IS NULL` rows count as active — `GET .../members` defaults to active-only, pass `includeLeft=true` for full history. Adding/removing a member itself requires the caller be staffed as PM on this project (see the `assertManagesProject()` bullet near the end of this section).
  - A member's `ProjectRole` (`PROJECT_MANAGER`/`DEVELOPER`/`DESIGNER`) must match the target user's actual global `Role` 1:1 — enforced by `ALLOWED_GLOBAL_ROLES` in `project-members.service.ts`. `Role` is the source of truth; `ProjectRole` just narrows it to the staffing context.
  - The "already a member" guard is scoped to `(project, user, role)`, not `(project, role)` — a project can have any number of different Developers/Designers/PMs active simultaneously; the only thing blocked is the _same_ user holding the _same_ role twice concurrently.
  - Availability (`EmployeeProfile.availabilityStatus`) is informational only — adding a member is never blocked by `BUSY`/`UNAVAILABLE`, and a member's own `User.status` (e.g. still `INVITED`, never logged in) isn't checked either.
  - **Auto status transition**: the moment a still-`PLANNING` project has both an active `PROJECT_MANAGER` and an active `DEVELOPER`/`DESIGNER`, `ProjectMembersService.autoTransitionFromPlanning()` moves it to `SCHEDULED` (future `plannedStartDate`) or `READY_FOR_WORK` (today/past/unset). This only fires on add and only while still `PLANNING` — a member later leaving never reverts it.
  - **Workload warnings are advisory only, never enforcing** — `RECOMMENDED_MAX_ACTIVE_PROJECTS` (`workload.constants.ts`, currently `3`) is shared by two call sites: adding a `DEVELOPER`/`DESIGNER` member returns a `workloadWarning` string in the response (not an error) if it pushes their active-project count (non-terminal `Project.status`) past the recommended max, and `GET /projects/mine`/`findForUser()` returns an `overloaded: boolean` flag for the same two roles. `PROJECT_MANAGER` is exempt from both — overseeing many projects at once is the job, not overload.
- **Documents (`ProjectDocument`)** — `ProjectDocumentsService`/`ProjectDocumentsController`, nested under `projects/:projectId/documents`. A document is either an uploaded `FILE` (Cloudinary, via `documentUploadOptions`) or typed `TEXT` (e.g. a `CREDENTIAL`) — never both, enforced in `create()`. `ProjectDocumentType` (`PRD`/`REQUIREMENT`/`MEETING_NOTE`/`CREDENTIAL`/`ASSET`/`DELIVERABLE`) drives the same read-scoping pattern as elsewhere in this module: `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` see everything, `DEVELOPER`/`DESIGNER` must be an active `ProjectMember`, and `CLIENT` is restricted to `DELIVERABLE`-type documents only (the `type` query filter is ignored for `CLIENT`) on their own project — enforced in `assertCanRead()`, duplicated per the same pattern as `assertActiveMember()` above rather than shared. Writes (`create`/`createBatch`/`update`/`remove`) are `PROJECT_MANAGER`-only (+auto `ADMIN`/`SYSTEM_ADMIN`) and additionally require the PM be staffed on this specific project (`assertManagesProject()`, see near the end of this section); `DEVELOPER`/`DESIGNER`/`CLIENT` are read-only here. Soft delete via `deletedAt`, same as `User`. `POST .../documents/batch` (`createBatch`, max `MAX_BATCH_UPLOAD_FILES` = 10) uploads files one at a time, not in parallel, specifically so the resulting `ProjectActivity` log entries stay in the same order the files were sent; every file becomes its own `ProjectDocument` row titled after its original filename and shares the same `type`/`description` — use the single-file `POST .../documents` instead for a distinct title per file or for a `TEXT`-format document.
  - **Documents are grouped by `(type, title)` into revision history, a convention rather than anything enforced on write** — reuploading under the same `title`/`type` is just a new row, not a replacement, so nothing stops a different title from ever being treated as its own separate current document. `GET .../documents` defaults to `includeHistory=false`: one row per `(type, title)` group, whichever has the newest `createdAt` (`findLatestPerGroup()`, Postgres `DISTINCT ON` via Prisma's `distinct`, re-sorted and paginated in application code since `count()` has no `distinct`-aware equivalent to pair with it). Pass `includeHistory=true` to get every revision of every group instead, flat and unfiltered by grouping. `GET .../documents/:id` always returns the single requested row, with a `supersededBy` field (`{ id, title, createdAt }` or `null`) naming the current newest row in its group when the requested one isn't it.
- **Time tracking (`TimeEntry`)** — `ProjectTimeEntriesService`/`ProjectTimeEntriesController`, nested under `projects/:projectId/time-entries`. Only `DEVELOPER`/`DESIGNER` track time (+auto `ADMIN`/`SYSTEM_ADMIN`, per the usual `Roles()` union — `PROJECT_MANAGER` is deliberately excluded from start/pause/resume/stop). A `TimeEntry` row is one running/paused/stopped **segment**, not a whole session — same append-only philosophy as `ProjectMember`/`ProjectActivity`: pausing never mutates a row back into a startable state, it closes the segment (`endedAt`/`durationMinutes` set, `status: PAUSED`) and `resume()` inserts a brand-new row instead, carrying the same `sessionId` forward (the first segment's `sessionId` equals its own `id`, generated via `randomUUID()` up front so it's known before insert). `resume()` rejects a segment that's already been superseded by a later resume (a newer row already shares its `sessionId`).
  - **"One active timer" is global per user, not per-project** — `start()`/`resume()` both reject with 409 if the caller already has any `TimeEntry` with `status: RUNNING` anywhere, regardless of project.
  - **Ownership is absolute** — `pause`/`resume`/`stop` all require `entry.userId === actorId`; unlike role-gating elsewhere, this is never bypassed by ADMIN/SYSTEM_ADMIN, mirroring `LeaveRequestsService`'s "only the requester cancels their own request."
  - **Read scope**: any active member of the project — `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` or a staffed `DEVELOPER`/`DESIGNER` — sees the whole team's entries by default on `GET .../time-entries`, matching the visibility documents/activities already had elsewhere in this module (deliberately _not_ self-scoped). `userId` is an optional filter anyone can use to narrow to one person (themselves or a teammate); `startDate`/`endDate` narrow to a whole-day-inclusive range (e.g. "how many hours did I work yesterday" is `startDate=endDate=<yesterday>`). The response includes `totalMinutes`/`totalHours` (summed over the same filters, not just the current page) alongside the usual paginated shape.
  - **A single continuous `RUNNING` stretch is capped at `MAX_CONTINUOUS_SESSION_MINUTES`** (`time-tracking.constants.ts`, currently 9 hours) — a safety net against a forgotten timer, not a background job: `autoStopIfExpired()` is checked lazily whenever a `RUNNING` entry is next touched (the owner's next `start`/`resume` attempt elsewhere, or that entry's own `pause`/`stop`), finalizing it as `STOPPED` with `durationMinutes` capped at exactly the limit (time worked beyond it is discarded, not carried over) and logging `TIME_AUTO_STOPPED`. Only `RUNNING` entries can expire this way — a `PAUSED` one already has its clock stopped. `GET .../time-entries` never triggers this itself (kept read-only), so a stale entry can still show as `RUNNING` in a list until the next write touches it.
  - **`GET .../time-entries/daily-summary`** answers "which developer worked how many hours, which day" — same scoping/filters as the list endpoint (`buildStartedAtFilter()` is a shared private helper so the two endpoints can't drift apart on date filtering), but grouped by the calendar day each segment's `startedAt` falls on (oldest first) instead of returned as a flat list. `userId` is optional for anyone: pass it to scope to one developer, omit it to combine the whole project team's hours per day. A segment that happens to straddle midnight is _not_ split across the two days — it's attributed entirely to the day it started, a deliberate simplification.
  - **`Project.actualHours`** is recalculated (summed `durationMinutes` across all `PAUSED`/`STOPPED` segments for that project, /60) every time a segment ends — on pause _and_ stop, not only on a final stop, since a paused segment's elapsed time is already real. `Project.estimatedHours` is a separate, manually-set field (`PATCH /projects/:id/estimated-hours`, `PROJECT_MANAGER`+auto `ADMIN`/`SYSTEM_ADMIN`; AI-assisted estimation is future work, not built). `remainingHours` is never stored — computed on the way out (`estimatedHours - actualHours`) via the shared `withRemainingHours()` helper in `projects.service.ts`, applied everywhere staff can see a project's hours (`findOne`, `findAll`, `findMine`, `findForUser`, `updateEstimatedHours`) — the same "derived on read, not persisted" convention as `days` on `Holiday`/`LeaveRequest`. `CLIENT`'s reduced `CLIENT_PROJECT_SELECT` view never includes hours at all.
  - **`GET /time-entries/active`** (`TimeEntriesController`, deliberately _not_ nested under `projects/:projectId` — see below) answers "do I have a timer running right now, and if so is it a project timer or a meeting timer" without needing a project id up front, since the one-active-timer rule is global across both `TimeEntry` and `MeetingTimeEntry`. Response shape is `{ active, kind: "PROJECT" | "MEETING" | null, entry }`. Reuses `ProjectTimeEntriesService.findActiveForUser()` rather than a second service, which itself checks `MeetingTimeEntry` directly (see "Meeting Time Tracking" below). `DEVELOPER`/`DESIGNER` can only check themselves; `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` may pass `userId` to check a specific team member. Also runs the auto-stop-if-expired check on whatever it finds, so checking this is itself another lazy-cleanup trigger point.
  - **`GET /time-entries/project-summary`** (same `TimeEntriesController`, also not project-nested) answers "which project takes how many hours" for one person, e.g. "Jabed: tool-internal 24.6h, target-board 5h" — grouped by project across _all_ of that user's projects, sorted most-hours-first, reusing `buildStartedAtFilter()` for the same optional `startDate`/`endDate` narrowing (both set to today answers "how many hours today, by project"). Unlike the project-scoped endpoints, self-view is unrestricted here — anyone can view their own; `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` may pass `userId` to view a specific developer/designer instead, 403 otherwise. Grouping is done in application code (fetch + `Map`), not a Prisma `groupBy`, since project names are needed in the response too.
- **Meeting Time Tracking (`MeetingTimeEntry`)** — `MeetingTimeEntriesService`, routes added to the existing `TimeEntriesController` (no new controller). Time not attached to any project, office meetings for now (`docs/features/time-meeting/DESIGN.md`, gitignored, has the fuller design writeup; `time-tracking-rules.md` in the same folder is the plain language, one sentence per rule summary of both this and the existing project time tracking rules). A sibling model to `TimeEntry` rather than a nullable `projectId` on it, since `TimeEntry.projectId` being required is relied on throughout `project-time-entries.service.ts`; shares the same segment shape and `TimeEntryStatus` enum so pause/resume mirrors `TimeEntry`'s append-only logic nearly line for line. `ADMIN`/`PROJECT_MANAGER`/`DEVELOPER`/`DESIGNER` can track meeting time (`PROJECT_MANAGER` is excluded from project time tracking but included here, since sitting in standups/planning is a PM's job even though billable project work isn't).
  - **Only one timer of any kind can run per person at once, across both `TimeEntry` and `MeetingTimeEntry`.** Starting a meeting timer while a project timer runs (or the reverse) is rejected with the same 409 pattern either table already uses for a second timer on itself. Built one directionally to avoid a circular dependency: `MeetingTimeEntriesService` depends on `ProjectTimeEntriesService` (a public `assertNoRunningProjectTimer()`) so `TimeEntry`'s real side effects (`recalculateActualHours`, `ProjectActivity` logging) stay in one place; `ProjectTimeEntriesService` does not depend back — it duplicates a small, side-effect-free finalize for an expired `MeetingTimeEntry` directly, since there's nothing there to keep in sync beyond the shared date math below.
  - **Meeting time never touches `Project.actualHours` or any project-scoped report.** It's its own number, shown alongside project hours on the endpoint below, never folded into them. No `ProjectActivity` rows are produced either, there's no project to log one against.
  - **`GET /time-entries/daily-summary`** (`TimeEntriesController`, not project-nested — distinct from `GET /projects/:projectId/time-entries/daily-summary`, which is one project grouped by day) answers the original ask: for each UTC calendar day in range, `projectMinutes` (summed across every project that day, via `ProjectTimeEntriesService.findDailyMinutesForUser()`) next to `meetingMinutes`, plus a `totalMinutes`, and grand totals across the range. Self-scoped for `DEVELOPER`/`DESIGNER`; `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` may pass `userId`.
  - **A segment must start and finish within the same UTC calendar day, for both `TimeEntry` and `MeetingTimeEntry`.** `getAutoStopCutoff()` (`time-entry-date.util.ts`) is `min(startedAt + 9 hours, endOfUtcDay(startedAt))` — whichever comes first finalizes a `RUNNING` segment, checked lazily wherever `autoStopIfExpired()` already ran (same no-cron-job convention as the 9-hour cap alone used to be). Once the day has passed, a `PAUSED` entry left over from it can no longer be paused, resumed, or stopped by hand (409) — a `RUNNING` one from a previous day is always caught by the cutoff above first, since the day-end cutoff is always in the past by the time anything touches it again.
  - `buildStartedAtFilter()` moved out of `ProjectTimeEntriesService` (where it used to live as a private method) into `time-entry-date.util.ts`, alongside `endOfUtcDay()`/`isPreviousUtcDay()`/`getAutoStopCutoff()`, since `MeetingTimeEntriesService` and the combined daily-summary endpoint need the exact same date semantics — the one exception to this module's usual "duplicate small checks per service" convention, since date math has no judgment call in it.
- **Additional Requirements (`AdditionalRequirement`)** — `AdditionalRequirementsService`/`AdditionalRequirementsController`, nested under `projects/:projectId/additional-requirements`. Logs a requirement received outside the system (email, Upwork/Fiverr, a client phone call) so a `PROJECT_MANAGER` (+auto `ADMIN`/`SYSTEM_ADMIN`) can decide whether to fold it into the project. Not client-visible at all — read access is `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` company-wide, or a staffed `DEVELOPER`/`DESIGNER` who is an active `ProjectMember` of that specific project (same `assertCanRead()` pattern as documents, minus the `CLIENT` branch).
  - **Every requirement requires an explicit PM approve/reject**, not just out-of-scope ones — the spec's automatic AI in/out-of-scope comparison (`aiScopeAnalysis` column) isn't wired up (no LLM provider integrated into this backend at all), so there's no scope flag to condition the approval flow on. `POST .../additional-requirements` creates a row as `PENDING_REVIEW`; `PATCH .../:id/review` (`PROJECT_MANAGER`+auto `ADMIN`/`SYSTEM_ADMIN` only) moves it to `APPROVED` or `REJECTED` and can only fire once — reviewing an already-reviewed row is a 409. Both routes additionally require the PM be staffed on this specific project (`assertManagesProject()`, see near the end of this section).
  - **Approving is additive, never an absolute override** — `approvedAdditionalHours` adds onto the project's current `estimatedHours` (treating a `null` estimate as 0), `deadlineExtensionDays` adds that many days onto the current `deadline` (treating a `null` deadline as "extend from today"). Both fields are rejected with a 400 if sent alongside a `REJECTED` decision — they only mean something when approving.
- **Daily Work Reports (`DailyWorkReport`/`DailyProjectEntry`)** — `DailyWorkReportService`/`DailyWorkReportController` (self-scoped, top-level routes) plus `ProjectDailyWorkReportsController` (project-nested read) and `DailyProjectEntryService` (PM review). One `DailyWorkReport` row per `(userId, date)` spans however many projects that person touches that day, each as its own `DailyProjectEntry` child row.
  - **Plan is mandatory before wrap-up** — `submitWrapUp()` throws 409 unless `status` is already `PLAN_SUBMITTED`; there's no way to wrap up a day that was never planned. Conversely, **wrap-up may include a project that was never in the morning plan** (unplanned/urgent work) — `submitWrapUp()`/`updatePlan()` `upsert` per project rather than requiring the row to already exist, so a wrap-up-only entry has `plan: null`.
  - **Two independent edit windows, one state-based and one time-based** — the plan is editable anytime up until wrap-up is submitted (`status === PLAN_SUBMITTED`, no time limit); the wrap-up is editable for a fixed 2 hours after `wrapUpSubmittedAt` (`WRAP_UP_EDIT_WINDOW_MS` in `daily-work-report.service.ts`), then locked for audit. These are two separate checks (`canEditPlan()`/`canEditWrapUp()`) — don't conflate them.
  - **Review (`PATCH .../entries/:entryId/review`)** is scoped to an active `PROJECT_MANAGER` member of that entry's _specific_ project (or auto `ADMIN`/`SYSTEM_ADMIN`) — same per-project-membership check as elsewhere in this module — and only allowed once the entry's report is `COMPLETED` (409 otherwise). A review only ever touches that one entry, never the rest of the report.
  - **Two list endpoints answer different questions** — `GET /projects/:projectId/daily-work-reports` (`DailyWorkReportService.findByProject()`) answers "who reported what on project X," scoped like documents/additional-requirements (`PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` company-wide, `DEVELOPER`/`DESIGNER` must be an active member); `GET /daily-work-reports` (`findAllForUser()`) answers "show me person Y's reports across every project they've touched," self-scoped for `DEVELOPER`/`DESIGNER` (403 if they request someone else's `userId`) or any-user for `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` — same self-vs-staff pattern as `ProjectTimeEntriesService.findActiveForUser()`. Both accept `type=PLAN`/`type=WRAP_UP` to filter to entries that only have a plan or only have accomplishments, and `startDate`/`endDate` (both inclusive; omit for all-time on the cross-project endpoint).
  - **"Today" is the current UTC calendar day, not the server's or caller's local timezone** — `toDateOnly()` (`daily-work-report.service.ts`) truncates via `Date.UTC(date.getUTCFullYear(), date.getUTCMonth(), date.getUTCDate())`, so the day boundary is always UTC midnight regardless of where the app is deployed or where the user sits. For Bangladesh (UTC+6) this means the day rolls over at 6am local time, not local midnight — someone submitting between 12am–5:59am Dhaka time gets dated the _previous_ day. This is never a problem for `submitWrapUp()`/`updateWrapUp()` specifically, since those are looked up by `reportId` (returned from the plan submission), not by recomputing "today" — a night-shift worker who plans at 11pm and wraps up at 7am the next UTC day still hits the same report. It would only surprise someone who tries to `POST /daily-work-reports` again after the UTC rollover before wrapping up their overnight shift, since that creates a genuinely separate report for the new day.
  - **Blockers are a fully independent entity, not a field on this model** — own lifecycle (`OPEN → IN_PROGRESS → RESOLVED`), can span multiple days, not tied to any single daily report. See "Real Time Blockers" below; `docs/features/daily-standups/` (gitignored — `DESIGN.md`, `README.md`, `ARCHITECTURE_NOTES.md`) has the fuller design writeup if this section doesn't answer the question.
- **Real Time Blockers (`Blocker`)** — `BlockerService` shared by `BlockersController` (top-level `blockers/*`) and `ProjectBlockersController` (`projects/:projectId/blockers`, PM dashboard read). Completely independent of `DailyWorkReport`/`DailyProjectEntry` — can be reported and resolved anytime, spans however many days it takes, not scoped to a calendar date. `DEVELOPER`/`DESIGNER`/`PROJECT_MANAGER` can report one (`POST /blockers`, status `OPEN`, `severity` defaults to `MEDIUM`), but only if actively staffed on that specific project (`assertCanReport()`) — `ADMIN`/`SYSTEM_ADMIN` bypass the staffing check and can report on any project.
  - **`reasonId` references `BlockerReason`, PM managed reference data** (`blocker-reasons.*`, routes under `/blocker-reasons`), defaulting to the seeded `"Unspecified"` row when a blocker is reported without one; that row is protected from rename and delete in `BlockerReasonsService`. Name uniqueness is enforced by a partial DB index over non deleted rows rather than a Prisma `@unique`, so a soft deleted reason's name can be reused, and a duplicate create/update returns 409, not a raw 500.
  - **Once `RESOLVED` a blocker is permanently locked** — `updateBlocker()`'s very first check rejects any further edit with 409, even for `ADMIN`/`SYSTEM_ADMIN`; this is the one terminal-state lock in this module that has no override.
  - **Editable by the original reporter or a `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN`, not by anyone else** — `assertCanUpdate()` checks `blocker.reportedById === actorId` first, then falls back to the PM-of-project check; a `DEVELOPER`/`DESIGNER` who didn't report it and isn't the PM gets a 403. The reporter can edit `description`/`severity` and move `status` themselves, including resolving their own blocker.
  - **Status moves are forward-only but may skip `IN_PROGRESS`** — `STATUS_ORDER` in `blocker.service.ts` rejects any move backward (e.g. `IN_PROGRESS → OPEN`) but allows `OPEN → RESOLVED` directly, since a blocker can be resolved before anyone marks it in progress. `resolutionNotes` is required exactly when resolving (400 if missing on resolve, 400 if sent without resolving) and sets `resolvedAt`/`resolvedById`.
  - **`assignedToId`/`assignedAt` track who is currently working the blocker**, separate from `reportedBy`/`resolvedBy`, since ownership can change hands (the reporter opens it, someone else takes it `IN_PROGRESS`, a third person resolves it). Moving `status` to `IN_PROGRESS` assigns the actor automatically if nobody is assigned yet; an explicit `assignedToId` in the request always wins instead and can reassign to any other active member of the project at any point before `RESOLVED`. Reassignment is logged as a `BLOCKER_ASSIGNED` activity.
  - **`deadlineExtensionDays` is an opt in decision made only when resolving**, additive onto `Project.deadline`, the same pattern as `AdditionalRequirement.deadlineExtensionDays`; it is rejected with a 400 if sent without `status: RESOLVED`. It is never derived from how long the blocker was open, so a blocker open for days doesn't move the deadline unless someone explicitly says so. `GET /projects/:projectId/blockers/deadline-impact` sums resolution time and extension days across a project's resolved blockers, using the same read scoping as the list endpoints below.
  - **`resolutionTime` (minutes), `daysOpen`, and `causedDeadlineExtension` are derived on read**, never stored — same convention as `days` on `Holiday`/`LeaveRequest` — computed in a private `withMetrics()` helper applied to every response.
  - **Reads are company-wide for `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN`, staffing-scoped for `DEVELOPER`/`DESIGNER`** — both `GET /blockers` and `GET /projects/:projectId/blockers` (the PM dashboard) are open to `DEVELOPER`/`DESIGNER`/`PROJECT_MANAGER` at the route level, but `BlockerService.findAll()`/`findByProject()` filter `DEVELOPER`/`DESIGNER` down to projects they're actively staffed on — only `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` see every project's blockers, matching how documents/additional-requirements/time-entries/daily-work-reports scope those same two roles elsewhere in this module. Editing a blocker (`assertCanUpdate()`) is separately PM-of-project-scoped — reads and writes use different gates here.
  - **Slack integration**: posts to the project's channel on report and on every status change, now also naming the current assignee once one is set. See "Slack integration" below (**Blockers**) for channel scoping, the no-`ts` behavior, and the rest of the shared plumbing.
- **Internal Review (`ProjectInternalReview`)**, `InternalReviewsService`/`InternalReviewsController`, nested under `projects/:projectId/internal-reviews`. The QA gate between a Developer/Designer finishing work and it going to the Client. A Developer/Designer moves a project `IN_PROGRESS → INTERNAL_REVIEW` via the existing generic `PATCH /projects/:id/status` (unchanged); a Project Manager (+auto `ADMIN`/`SYSTEM_ADMIN`, staffed as PM on this specific project via `assertManagesProject()`) then submits a decision via `POST .../internal-reviews`, which is the only path that can move a project out of `INTERNAL_REVIEW` into `READY_FOR_CLIENT`/`READY_FOR_WORK`. `ALLOWED_STATUS_TRANSITIONS.INTERNAL_REVIEW` in `projects.service.ts` no longer lists either as a transition the generic endpoint can make (only `CANCELLED` still is).
  - **Every decision creates a new `ProjectInternalReview` row**, never overwritten. `reviewRound` increments per project (`count + 1`, enforced unique via `@@unique([projectId, reviewRound])`), so the full round by round history survives. `APPROVED` moves the project to `READY_FOR_CLIENT`; `CHANGES_REQUIRED` moves it back to `READY_FOR_WORK`. `comments` is required specifically when requesting changes (400 otherwise), the same "reason required for this specific outcome" convention as `Blocker.resolutionNotes` on resolve and `ON_HOLD`'s required `reason`, so the developer/designer has something actionable to fix. Logs both `INTERNAL_FEEDBACK_RECEIVED` and `STATUS_CHANGED` activities, the latter shaped identically to what `ProjectsService.updateStatus()` itself logs.
  - **Reads follow the same pattern as Additional Requirements.** `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` see any project's review history; `DEVELOPER`/`DESIGNER` must be an active `ProjectMember`; `CLIENT` is excluded entirely (internal only, not part of the Client Feedback flow below). `GET .../internal-reviews` is ordered oldest round first.
- **Client Feedback (`ClientFeedback`)**, `ClientFeedbackService`/`ClientFeedbackController`, nested under `projects/:projectId/client-feedback`. The step after Internal Review: once a project is `READY_FOR_CLIENT` a Project Manager moves it to `WAITING_FOR_FEEDBACK` via the existing generic `PATCH /projects/:id/status`, then the Client (or a PM staffed on this project, recording feedback the Client gave outside the system) submits a decision via `POST .../client-feedback`.
  - **Only the first round for a project moves `Project.status`** (`APPROVED` to `COMPLETED`, setting `completedAt`; `CHANGES_REQUESTED` to `READY_FOR_WORK`), and it requires the project currently be `WAITING_FOR_FEEDBACK` (409 otherwise). Every later round is commentary only: accepted regardless of the project's current status (blocked only once `COMPLETED`/`CANCELLED`) but never touches `Project.status` again, so a developer already back `IN_PROGRESS` on the first round's decision is never interrupted by later client input. `comments` is required exactly when `decision` is `CHANGES_REQUESTED`, the same convention as `Blocker.resolutionNotes` and `ProjectInternalReview.comments`. `feedbackRound` increments per project (`existingCount + 1`), so the full history survives; each round logs a `CLIENT_FEEDBACK_RECEIVED` activity (plus `STATUS_CHANGED` on the first round).
  - **Reads differ from Internal Review in exactly one way: `CLIENT` is included, not excluded.** `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` see any project's feedback history; `DEVELOPER`/`DESIGNER` must be an active `ProjectMember`; `CLIENT` must be this project's own client (`project.clientId === actorId`). `GET .../client-feedback` is ordered oldest round first, same as internal reviews.
  - **Writes are `PROJECT_MANAGER`/`CLIENT` only** (`ADMIN`/`SYSTEM_ADMIN` bypass via the usual `Roles()` union), with `DEVELOPER`/`DESIGNER` excluded at the controller's `@Roles` level, never reaching the service. A submitting `PROJECT_MANAGER` must be staffed as PM on this specific project (same `ProjectMember` check as `assertManagesProject()` elsewhere, though implemented locally in `ClientFeedbackService` rather than shared); a submitting `CLIENT` must be this project's own client. `recordedById` is set to the actor for a PM submission, `null` for a direct Client submission, so the two cases stay distinguishable on read.
  - `ALLOWED_STATUS_TRANSITIONS.READY_FOR_CLIENT`/`WAITING_FOR_FEEDBACK` in `projects.service.ts` intentionally omit `WAITING_FOR_FEEDBACK → COMPLETED`/`READY_FOR_WORK` from the generic status endpoint. Only `ClientFeedbackService.create()`'s first round can make either move, so a `ClientFeedback` record always exists to explain how a project left `WAITING_FOR_FEEDBACK`, the same pattern `INTERNAL_REVIEW`'s transitions use for `ProjectInternalReview`.
- `ProjectActivityService` (`project-activity.service.ts`) is the single place that writes `ProjectActivity` rows, shared by `ProjectsService`, `ProjectMembersService`, `ProjectDocumentsService`, `ProjectTimeEntriesService`, `AdditionalRequirementsService`, `DailyWorkReportService`/`DailyProjectEntryService`, `BlockerService`, `InternalReviewsService`, and `ClientFeedbackService` rather than duplicated per-feature. `ProjectActivityType` is deliberately scoped to what the app can produce today — extend the enum (+ a hand-written migration, see the Prisma note above) as new features land, the same way `TIME_STARTED`/`TIME_PAUSED`/`TIME_RESUMED`/`TIME_STOPPED`/`ESTIMATED_HOURS_CHANGED`/`ADDITIONAL_REQUIREMENT_ADDED`/`ADDITIONAL_REQUIREMENT_REVIEWED`/`PLAN_SUBMITTED`/`PLAN_UPDATED`/`WRAP_UP_SUBMITTED`/`WRAP_UP_UPDATED`/`WORK_REPORT_REVIEWED`/`BLOCKER_ADDED`/`BLOCKER_STATUS_CHANGED`/`BLOCKER_ASSIGNED`/`INTERNAL_FEEDBACK_RECEIVED`/`CLIENT_FEEDBACK_RECEIVED` were added as their features landed.
- `GET /projects` filters by `status`/`priority`/`clientId`/`projectTypes` — `projectTypes` accepts one or more values (comma-separated or repeated query keys) and matches **ANY** of them (`some`/`in`), not all of them. It also takes `archived` (boolean, default `false`, excludes archived projects; `true` gives a dedicated archive only view rather than a mix of both) and `search` (case insensitive, matches anywhere in `name`) via `QueryProjectsDto`.
- Create/list-all/update/priority/types/staffing-mutation routes stay staff-only at the route level: `PROJECT_MANAGER` (+auto `ADMIN`/`SYSTEM_ADMIN`). `PROJECT_STAFF_ROLES` is defined separately in `projects.controller.ts` and `project-members.controller.ts` (not shared) — keep both in sync if the access list ever changes. `archive`/`restore` are the one exception: `@Roles([Role.ADMIN])` only (so also `SYSTEM_ADMIN`, per the `Roles` union, but never plain `PROJECT_MANAGER`), matching their `assertIsAdmin()` check at the service layer (see below).
- **PM mutations require being staffed as PM on that specific project, not just holding the role company-wide** — a private `assertManagesProject()` (ADMIN/SYSTEM_ADMIN bypass; else requires an active `ProjectMember` row with `role: PROJECT_MANAGER` on that project, else 403) is duplicated across `ProjectsService` (update/updatePriority/updateEstimatedHours/updateTypes/connectSlackChannel, plus the PM branch of `updateStatus` via `assertCanChangeStatus`), `ProjectMembersService` (add/remove), `ProjectDocumentsService` (create/createBatch/update/remove), and `AdditionalRequirementsService` (create/review) — same duplication convention as `assertActiveMember()` below. Reads on all of these stay company-wide for PM; only writes are staffing-scoped. `PATCH /projects/:id/status` is the one exception with two branches: PM goes through `assertManagesProject`, DEVELOPER/DESIGNER go through `assertActiveMember` instead (any staff role, not PM-specifically) — see `assertCanChangeStatus()`. `archive`/`restore`/the `isReopening` branch of `updateStatus` use a separate, stricter `assertIsAdmin()` check instead (ADMIN/SYSTEM_ADMIN only, no PM bypass) — staffing on the project is irrelevant to those three.
  - **Bootstrapping**: `ProjectsService.create()` auto-staffs the creating PM as an active `PROJECT_MANAGER` `ProjectMember` on their own new project (logged as a `MEMBER_JOINED` activity) — otherwise they'd be locked out of editing a project the instant they created it, since a brand-new project has zero staff. `ADMIN`/`SYSTEM_ADMIN` creators are _not_ auto-staffed (unscoped access already covers them, and they don't hold the `PROJECT_MANAGER` global role `ALLOWED_GLOBAL_ROLES` would require for that `ProjectMember` row). A second PM can only be added by `ADMIN`/`SYSTEM_ADMIN` or by a PM already staffed on that project — there's no self-service path for an unstaffed PM to add themselves.
- **Single-project reads are scoped to the caller, not just role-gated** — `findOne`/`findActivities` (`ProjectsService`) and `findAll` (`ProjectMembersService`, the member list) all call a private `assertActiveMember()` (duplicated in both services, same pattern as the `PROJECT_STAFF_ROLES` duplication above): `PROJECT_MANAGER`/`ADMIN`/`SYSTEM_ADMIN` can read any project; `DEVELOPER`/`DESIGNER` must be an active `ProjectMember` of that specific project or get a 403. `CLIENT` is handled separately in `findOne` (see below) and is excluded entirely from `findActivities` and the member list (internal-only views).
- **`CLIENT` gets a reduced field set, not the full `Project` row** — `CLIENT_PROJECT_SELECT` in `projects.service.ts` strips internal fields (`priority`, `rushReason`, `onHoldReason`, `cancellationReason`, `createdBy`) down to `id`/`name`/`description`/`status`/`plannedStartDate`/`deadline`/`completedAt`/`createdAt`/`projectTypeTags`, matching the spec's "a Client can view only the status of their own projects." It does not join in documents — a `CLIENT` fetches their `DELIVERABLE`-type documents separately via `GET /projects/:id/documents` (see "Documents" below), not as part of this payload.
- **`GET /projects/mine`** is one endpoint whose scope and field set both branch on the caller's role: `CLIENT` → projects where they're the `clientId` (client field set, newest-first, `archived` filter ignored); `PROJECT_MANAGER`/`DEVELOPER`/`DESIGNER` → projects where they have an active `ProjectMember` row, sorted in JS (not a DB `orderBy`, since the ordering needs a computed active-status bucket Prisma can't express directly) by `compareForDashboard()`: active status (`READY_FOR_WORK`/`IN_PROGRESS`) first, then `Priority`, then `Deadline`, then `Planned Start Date` — the exact order the spec's Developer/Designer Dashboard calls for. Takes the same `archived` filter as `GET /projects` (via `QueryMyProjectsDto`, default `false`) for the staff branch too. `GET /projects/users/:userId` (`ProjectsService.findForUser()`, PM/ADMIN/SYSTEM_ADMIN checking a specific person's workload) shares this same `archived`-aware `findByActiveMembership()` logic rather than duplicating it. Must be declared before `GET /projects/:id` in the controller or Nest/Express would swallow `/projects/mine` as `:id === "mine"`.
- Not built yet: the AI in/out-of-scope comparison for Additional Requirements (see above). Internal Review and Client Feedback (see above) are both built. Slack integration (see "Slack integration" below) **is** built — per-project private channels synced to `ProjectMember` staffing, plus a fixed company-wide feed channel for daily plan/wrap-up posts, wired into project creation, staffing, daily work reports, and blockers — per `docs/features/slack-integration/DESIGN.md`/`IMPLEMENTATION_CHECKLIST.md` (both gitignored). `pixelvega-build-spec.md` (repo root) tracks this module specifically — a Prisma-flavored draft schema with each model/field marked IMPLEMENTED or NOT YET BUILT against the real `schema.prisma`; treat it as directional rather than exact since it isn't always updated in the same commit as the code.

### Slack integration

- `src/modules/slack/` — `SlackModule` (not `@Global()`; `ProjectsModule` imports it to inject `SlackService`/`SlackUserResolverService`). `SlackService` wraps `@slack/web-api`'s `WebClient`, same shape as `MailService` — every method catches and logs its own errors and **never throws**, since nothing in this feature is allowed to fail an unrelated request: `createProjectChannel`, `inviteToChannel`, `removeFromChannel`, `postMessage`, `updateMessage`, `lookupUserIdByEmail`, `verifyChannelAccessible`.
- **Resolving a user's Slack id** is centralized in `SlackUserResolverService.resolveSlackUserId()`: returns the cached `User.slackUserId` if already set, else calls `lookupUserIdByEmail()` and caches the result on success, else `null`. Every call site (project creation, staffing add/remove, the resync endpoint below) goes through this one method rather than duplicating the cache-then-lookup logic.
- **Channel creation happens once, at project-creation time**: `ProjectsService.create()` fires an un-awaited `syncSlackChannelForNewProject()` which builds the channel name (`buildChannelName()` in `slack-channel-naming.util.ts` — sorted+slugified `ProjectType`s + slugified project name, 80-char Slack limit, retries on `name_taken` up to `MAX_NAME_COLLISION_ATTEMPTS`), creates the channel, saves `Project.slackChannelId`, and invites the auto-staffed PM plus every current `ADMIN`/`SYSTEM_ADMIN` — a one-time roster snapshot, not a standing sync. If this fails (misconfigured token, Slack API down), the project is simply left with `slackChannelId: null` forever — there's no automatic retry, which is why the backfill endpoint below exists.
- **Staffing sync**: `ProjectMembersService.add()`/`remove()` invite/remove the member's Slack account from the project channel (no-op if the project has no channel, or the user's Slack id can't be resolved) — also fire-and-forget, logged on failure, never blocking the staffing change itself.
- **Two backfill/resync endpoints exist because the automatic paths above only ever run once and never retry**:
  - `POST /projects/:projectId/members/:memberId/resync-slack` (`ProjectMembersService.resyncSlackChannelMembership()`) — re-resolves and re-invites an existing active member, for when they didn't have a Slack account (or used a different email) at the time they were originally staffed. Returns `{ invited: boolean, message }` rather than an error when no Slack account resolves yet.
  - `PATCH /projects/:id/slack-channel` (`ProjectsService.connectSlackChannel()`) — backfills a channel for a project that never got one. Omit `slackChannelId` in the body to auto-create a new channel (same naming logic as creation-time); pass one to link a channel someone already made by hand in Slack (verified accessible via `SlackService.verifyChannelAccessible()` — `conversations.info`, rejects archived/inaccessible channels with 400). Either way, invites the **current** full active roster + admins, not just whoever was staffed at creation time. 409 if the project already has a channel — no silent relink.
- **Daily Work Reports** (`DailyWorkReportService`) post to the project's channel **per project entry** (`planProjectSlackTs`/`wrapUpProjectSlackTs` on `DailyProjectEntry`, one message per project) but to the feed channel (`SLACK_DAILY_FEED_CHANNEL_ID` env var) as **one combined message per report**, covering every project the author touched that day — `planFeedSlackTs`/`wrapUpFeedSlackTs` live on `DailyWorkReport`, not `DailyProjectEntry`. `syncCombinedPlanFeedMessage()`/`syncCombinedWrapUpFeedMessage()` always re-fetch the report's _current_ full set of entries and rebuild the whole combined message from scratch — called after every `create()`/`submitWrapUp()`/`updatePlan()`/`updateWrapUp()`, not just when the specific call touched every project — so editing one project's plan still regenerates the entire combined feed message, not just that project's line. Per-project channel messages (`updateEntryPlanProjectMessage()`/`updateEntryWrapUpProjectMessage()`) are still edited individually via `updateMessage()` using their own stored `ts`. Both the per-project and combined-feed paths share the same fallback: if a channel exists but no `ts` was ever stored for it yet (e.g. the project's channel didn't exist at original submission time and was only connected afterward via the backfill endpoint above, or the feed channel wasn't configured yet), they post a fresh message instead of silently skipping, and persist the new `ts` for later edits.
- **Blockers**: `BlockerService.addBlocker()`/`updateBlocker()` post to the project channel only (never the feed channel), and never store/update a `ts` — each status change is treated as its own new event, not an edit of a prior message.
- **One-directional only** — there is no inbound webhook/Events API endpoint anywhere in this backend. Editing a message directly in Slack never syncs back to the database; the next time our system posts an update, it overwrites Slack's content with whatever the DB currently holds.
- Env vars: `SLACK_BOT_TOKEN`, `SLACK_DAILY_FEED_CHANNEL_ID`. Every `SlackService` call safely no-ops without a valid token, so this feature can be deployed/merged even before a real Slack app/workspace exists.

### AI integration

- `src/modules/ai/` — `AiModule` (not `@Global()`; imported by `ProjectsModule`). `docs/features/ai-integration/DESIGN.MD` and `IMPLEMENTATION_CHECKLIST.md` (both gitignored) have the fuller technical design and phase by phase build history. Three features, covering scope checking, a quick project summary, and a saved status report, all backed by the same `ClaudeService`.
- **`ClaudeService`** (`claude.service.ts`) is the only file in the whole codebase that touches `@anthropic-ai/sdk`. `generateText()`/`generateStructured<T>()`, model `claude-haiku-4-5` throughout. `generateStructured()` parses the returned text as JSON itself rather than relying on the SDK's own convenience property, so a malformed response surfaces as a clear parse error. Claude's own `output_config.format.schema` does not support `minimum`/`maximum` on a `number` property (found by testing, not documented anywhere up front); range constraints go in the property `description`/system prompt instead.
- **`buildDocumentContent()`** (`document-content.util.ts`), shared by all three features, turns a `ProjectDocument` into whatever Claude actually reads: a `TEXT` format document becomes a plain text block; a `FILE` format PDF is fetched fresh from `fileUrl` and sent as a native `document` content block (base64), no extraction/markdown conversion step, no RAG, no chunking, no embedding, anywhere in this design (a PRD here typically runs 3 to 4 pages, short enough to send in full every time). Word/Excel/PowerPoint/zip have no native Claude content block and are skipped, returning `null`.
- **Feature 1, scope checker**: `POST /projects/:projectId/additional-requirements/:id/check-scope` (`AdditionalRequirementsService.checkScope()`, PM staffed on this project + auto Admin/System Admin), enqueues `CHECK_SCOPE`, returns `{ jobId }`. The actual comparison (`ScopeCheckService.handle()`, `src/modules/ai/scope-check.service.ts`) compares the requirement's own description against the project's PRD/REQUIREMENT documents, asks Claude for a structured `{ verdict, confidence, reasoning, suggestedAdditionalHours }`, and writes it to the already existing `AdditionalRequirement.aiScopeAnalysis` column. If the project has neither PRD nor REQUIREMENT documents, no Claude call is made at all, but `aiScopeAnalysis` still gets a real `reasoning` string explaining why, never left bare `null`. Calling it again on the same requirement overwrites the previous result, it is advisory context, not an append only history table, and never gates approval, `AdditionalRequirement.approvedAdditionalHours` is still only ever set by a PM's own `PATCH .../:id/review`.
- **Feature 2, project summary**: `GET /projects/:projectId/ai/summary` (`src/modules/projects/ai-summary/`), synchronous, no queue, same read scoping as the rest of `ProjectsModule` (PM/Admin/System Admin any project, staffed Developer/Designer only, Client excluded). Combines the project's PRD (if any) with `DailyProjectEntry.accomplishments` (deliberately never `.plan`, since a plan is stated intent that may not have happened) for a given date range, plus the open blocker count and core snapshot from `ProjectReportService.getProjectReport()` (see "Project management" above). Generated fresh every call, nothing is ever stored. A project with nothing accomplished yet in range still returns a thin, real summary, never an error.
- **Feature 3, AI status report**: `POST`/`GET /projects/:projectId/ai/status-reports` (`src/modules/projects/ai-status-reports/`), the saved, fuller counterpart to Feature 2, meant to be handed to a client or leadership. `POST` (PM staffed on this project + auto Admin/System Admin) enqueues `GENERATE_STATUS_REPORT`, period defaults to since the project's last status report, or the last seven days if it has never had one (clamped so the computed default `periodStart` can never land after `periodEnd`, a real edge case found during testing). Includes both `plan` and `accomplishments` text (planned versus delivered, unlike Feature 2), plus the full `ProjectReportService` numeric report, reused rather than recalculated so the two can never disagree. Every generation saves a new `ProjectStatusReport` row, append only, never overwritten; `GET` lists history newest first with the same read scoping as Feature 2.
- **Background jobs**: one BullMQ queue, `'ai-jobs'` (`AiJobsService.enqueue()`/`findOneScoped()`, `src/modules/ai/ai-jobs.service.ts`), one shared `AiJobsProcessor` (`@Processor('ai-jobs')`) dispatching on `job.name` into `ScopeCheckService`/`StatusReportService`, rather than each feature registering its own competing processor, BullMQ expects exactly one worker per queue name. `GET /ai-jobs/:id` polls a job's `AiJob` row (`QUEUED`→`PROCESSING`→`COMPLETED`/`FAILED`, `resultRefId`/`errorMessage`), access checked against whatever the underlying feature would have required. Requires `REDIS_URL` reachable (a local `redis-server` in development); the connection is built with `lazyConnect: true` so an unreachable Redis fails the first job rather than blocking app boot.
- **Circular dependency avoidance**: `ScopeCheckService`/`StatusReportService` live inside `AiModule`, not `ProjectsModule`, specifically so the shared `AiJobsProcessor` (also in `AiModule`) can dispatch to them without `AiModule` needing to import `ProjectsModule` (which already imports `AiModule` the other way, for `AiJobsService`/`ClaudeService`/`AiTemplatesService`). The status report handler genuinely needs `ProjectReportService`'s numbers (unlike the scope checker), solved by computing that snapshot once in `ProjectsModule`, at enqueue time, and passing it through as plain JSON on `AiJob.input`, so the handler itself never depends back on `ProjectsModule`.
- **`AiTemplate`** (`AiTemplatesService`/`AiTemplatesController`, both in `AiModule`) is reference data shaping Feature 2/3's output: one `kind` per feature (`PROJECT_SUMMARY`, `STATUS_REPORT`), exactly one `isDefault: true` row per kind (partial unique index, same approach `BlockerReason` uses), `content` is a structural outline (e.g. `## Executive Summary\n...`) dropped directly into Claude's system prompt, no templating engine or variable substitution. `GET /ai-templates` any staff role, `POST`/`PATCH`/`DELETE` Admin/System Admin only. The scope checker (Feature 1) does not use a template at all, its system prompt is fixed in code, since its output is a strict structured schema, not free prose.
- Env vars: `ANTHROPIC_API_KEY`, `REDIS_URL`.

### Notifications

- `src/modules/notifications/` — `NotificationsModule` is `@Global()` (same pattern as `AuditLogModule`), and imports `SlackModule` for the optional Slack DM channel and the deadline reminder's project channel post, a one directional dependency, `SlackModule` has no dependency back on this module. `docs/features/notifications/DESIGN.md` and `docs/notification-build-spec.md` (both gitignored) have the fuller technical design and the plain business level spec respectively.
- `NotificationsService.notify({ userId, type, title, message?, metadata?, slackDm? })` is the one place that writes a `Notification` row, called explicitly at the point something actually happens (`ProjectsService`, `ProjectMembersService`, `ProjectDocumentsService`, `BlockerService`, `DailyProjectEntryService`, `InternalReviewsService`, `ClientFeedbackService`, `AdditionalRequirementsService`, `LeaveRequestsService`, `ScopeCheckService`), the same explicit call convention `ProjectActivityService`/`AuditLogService` already use rather than a generic request interceptor.
- **One row per recipient, not one shared row multiple people read.** The same event (a project's status changing, for example) fans out into a separate `Notification` row for every recipient, since a notification is inherently per person, unlike `ProjectActivity`, which is one row read by everyone with project access.
- **`NotificationType` is one value per distinct event, never a generic bucket** ("assigned to a new project" and "reassigned to the same project" stay separate types even though both could be described as "staffing changed"). Who receives a given type is a recipient rule resolved by whichever service fires it, not baked into the type itself.
- **Two shared recipient resolvers on `NotificationsService`, reused across almost every trigger site**: `resolveManagingPmAndAdminIds(projectId)` (every active `PROJECT_MANAGER` staffed on that project, plus every `ADMIN`/`SYSTEM_ADMIN` company wide) and `resolveAllActiveMembersAndAdminIds(projectId)` (every active `ProjectMember` of any role, plus Admin/System Admin). The acting user is excluded from these lists at nearly every call site, so nobody gets notified about their own action. The one exception is `ADDITIONAL_REQUIREMENT_FLAGGED_OUT_OF_SCOPE`, where Claude, not the requesting PM, is the one making the determination, so the requester is notified too.
- **Delivery is always in app, plus optionally Slack.** `notify({ slackDm: true })` fires a fire and forget Slack direct message (never awaited by the caller, caught and logged on failure, never thrown), resolved via the existing `SlackUserResolverService.resolveSlackUserId()` and posted via the existing `SlackService.postMessage(slackUserId, text)` unchanged, `chat.postMessage` treats a user id passed as `channel` as opening a DM, no new Slack API call needed. Only wired into the four events the build spec marks for it: `MEMBER_HANDOVER`, `PROJECT_READY_FOR_CLIENT`, `CLIENT_FEEDBACK_APPROVED`, `CLIENT_FEEDBACK_CHANGES_REQUESTED` (the last two DM only the PM/Admin subset of the broader recipient list, the Developer/Designer side of those two events is in app only). A project channel post is a separate, direct `SlackService.postMessage(project.slackChannelId, text)` call from whichever service fires the event, never routed through `notify()` itself, since a channel post is per project, not per recipient, the deadline reminder below is the one example of this today.
- **`GET /notifications` / `GET /notifications/unread-count` / `PATCH /notifications/:id/read` / `PATCH /notifications/read-all`** are always self scoped, no `@Roles()` restriction at all (the same open to any authenticated user pattern `GET /profiles/me` already uses). A user only ever sees their own rows, no staff role sees anyone else's. Polling, not real time push, is the deliberate v1 choice, nothing else in this backend pushes to the frontend in real time either.
- **Two scheduled reminders**, `NotificationsSchedulerService`, `@nestjs/schedule`, both pinned to `Asia/Dhaka`: `STANDUP_MISSED` (9:30 AM, every `DEVELOPER`/`DESIGNER`/`PROJECT_MANAGER` with no `DailyWorkReport` row for today) and `WRAP_UP_MISSED` (11 PM, every report still `PLAN_SUBMITTED`, not `COMPLETED`), both skip Friday, checked via `Intl.DateTimeFormat` against the real Asia/Dhaka weekday rather than the existing UTC day indexed `WEEKLY_OFF_DAY`, which would not reliably match the local calendar day. `DEADLINE_APPROACHING` (9 AM, every non terminal project exactly two calendar days from its deadline) is deliberately not skipped on Friday, a deadline two days away is real regardless of the day. Every scheduled check dedupes against today's own `Notification` rows first, a restart mid cron window must never double notify, and the deadline reminder's project channel post additionally only fires when at least one recipient was actually, newly notified that run.
- Env var: none new, reuses `SLACK_BOT_TOKEN` from Slack integration above for the DM/channel delivery.

### Module layout

- `src/auth/` — the shared `betterAuth()` instance (`auth.instance.ts`) and its hook providers. This is infra, not a Nest module — imported directly wherever `auth.api.*` is needed (`users.service.ts`, `auth.service.ts`).
- `src/prisma/` — `PrismaModule` is `@Global()`; inject `PrismaService` anywhere without re-importing the module.
- `src/common/` — cross-cutting decorators (`@CurrentUser()` reads `request.user`, set by the global `AuthGuard`), utils (temp-password gen, 6-digit reset-code gen/hash), and the hand-written Swagger paths for better-auth's own routes.
- `src/modules/<feature>/` — each feature is `*.module.ts` / `*.controller.ts` / `*.service.ts` / `dto/` (see `leave/`, `audit-log/`, `profiles/`). This is the default shape for a new, independent feature — but anything that needs `ProjectActivityService`/`ProjectMember` checks stays registered in the existing `ProjectsModule` instead (see "Project management" above): a separate module here would spin up its own DI instance of `ProjectActivityService`, splitting the project-domain activity log across two instances. - `src/modules/leave/` — three controllers (`leave-requests`, `leave-types`, `holidays`) and four providers in one `LeaveModule`, not split into separate feature modules; see "Leave management" above.

Every feature that needs `ProjectActivityService`/`ProjectMember` checks lives in this one module, for the DI reason noted under "Module layout" above, organized on disk into the per-feature subfolders described there (`members/`, `documents/`, `time-tracking/`, `additional-requirements/`, `daily-work-reports/`, `blockers/`, `internal-reviews/`, `client-feedback/`), not one flat folder.

The HTTP triggers/permission checks for Feature 2/3 live in `src/modules/projects/ai-summary/`/`ai-status-reports/` instead, inside `ProjectsModule` itself. See "AI integration" above.
- `src/modules/notifications/` — `NotificationsModule` is `@Global()`, imports `SlackModule` for the optional Slack DM/channel delivery. See "Notifications" above.

### API docs

Swagger UI at `/api/docs` (JSON at `/api/docs-json`). Add `@ApiProperty()`/`@ApiPropertyOptional()` to new DTO fields and `@ApiOperation`/`@ApiResponse` to new controller methods to keep it complete. If a new endpoint is handled outside a Nest controller (like better-auth's own routes), add it by hand in `src/common/swagger/better-auth-paths.ts` rather than expecting it to be discovered.

Each controller in `src/modules/projects/` has its own `@ApiTags(...)` (`Projects`, `Project Members`, `Project Documents`, `Time Tracking`, `Additional Requirements`, `Daily Work Reports`, `Blockers`, `Blocker Reasons`, `Internal Reviews`, `Client Feedback`) rather than sharing one generic `Projects` tag — this groups the Swagger UI by feature so a frontend consumer can navigate by concern instead of scrolling one long list. Give any new project-domain controller its own tag rather than reusing `Projects`.

`postman/` (repo root, gitignored, see below) holds hand-built Postman collections, each covering one feature slice rather than one collection mirroring every `@ApiTags` group: `PMT Backend - Projects Final.postman_collection.json` (Projects/Project Members/Project Documents only) and `PMT Backend - Time Tracking.postman_collection.json` (project + meeting time tracking). Follow the existing collections' conventions when adding a new one: `{{baseUrl}}` variable set to `http://localhost:5050/api`, real ids from the dev DB as default variable values rather than placeholders, and rely on Postman's own cookie jar for the session cookie after a `Sign In`/`POST {{baseUrl}}/auth/sign-in/email` request rather than wiring a `Cookie` header on every request.

## Code style

Favor straightforward, easy-to-read code over clever or maximally-compact code — explicit variable names, simple conditionals, small functions that do one obvious thing, in the style of the existing modules (compare `users.service.ts` or `profiles.service.ts`). It's fine for something to take a few more lines if that makes it easier to follow. This applies to logic/control-flow only — folder layout, module boundaries, and DTO/service/controller separation should still follow the patterns in "Module layout" above so the codebase stays easy to extend as new features (standups, etc.) are added.

**Never use a hyphen or em dash (`-`, `—`) in any prose you write in this project**: markdown docs, this file, code comments, and API text (Swagger `description`/`summary`, Postman request/collection descriptions). This covers both clause connecting punctuation (write "X, so Y" rather than "X, Y" with a dash joining them) and compound word hyphens where a rephrase is easy ("read only" rather than the hyphenated form, "company wide" rather than the hyphenated form). Use a period, comma, colon, parentheses, or a reworded phrase instead. This does not apply to file/folder names (kebab case is the NestJS convention), API route paths and query params (already hyphenated as part of the contract), code identifiers, git branch names, or a `->`/`→` arrow used to denote a state transition. Existing text written before this rule was added is not retroactively rewritten on its own; only apply the rule going forward, to anything newly written.
